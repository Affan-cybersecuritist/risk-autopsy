# Engineering Log — Risk Autopsy

The main README keeps the five strongest engineering discoveries. This is the complete history — every real bug found and fixed during development, in chronological order. It exists so the project's engineering rigor is demonstrable in full without turning the primary pitch document into a debugging diary.

1. **Temporal leakage** — an early feature set included `return_rate`/`return_lag` (i.e., "did the loss already happen"), correlation 0.88+ with the label. Removed; all features are now restricted to information available *before* any return/chargeback.
2. **Cluster leakage in evaluation** — abuse-ring siblings could appear in both train and test. Fixed with a ring-grouped split.
3. **Unrealistically clean synthetic signal** — device/address sharing was a perfect (1.000 correlation) signal because only rings ever shared anything. Added realistic legitimate household sharing (capped at 2-4 members after an early version let chance create an 11-person "household").
4. **Cross-realm `IntersectionObserver` bug** (frontend, since fixed and superseded by the React rebuild) — an observer created inside a sandboxed iframe silently never fired when observing parent-document elements, leaving UI cards permanently invisible. Fixed by using the correct window's constructor.
5. **Silent camera-permission hang** (current `webapp/`) — `getUserMedia` waits on a one-time browser permission prompt; the UI previously gave no feedback during that wait. Fixed with an explicit status message.
6. **`tsc -b` (the real build command) was broken while `tsc --noEmit` passed** — a recharts `Tooltip formatter` type mismatch only surfaced under project-reference build mode, which the dev server never runs. Would have shipped a broken production build undetected. Fixed the formatter's typing; `npm run build` is now part of the standard verification pass, not just the dev server staying green.
7. **2.53MB main JS bundle** — face-api.js and the react-three-fiber background were both imported statically and loaded on first paint even though neither is needed until a user actually interacts (opens the approval modal, scrolls past the hero). Dynamic-imported both; main bundle dropped to 1.0MB.
8. **ReportLab's default font has no ₹ glyph** — silently rendered as a black-box placeholder character in the compliance PDF instead of erroring. Fixed by using "Rs." in PDF-only currency formatting; regression test now asserts no missing-glyph boxes ever ship in a generated dossier.
9. **Section 5's "Submit for human approval" button was entirely cosmetic** — found in the same self-audit as #10 below. Its `onApproved` handler set a display label from client input and never called the backend at all, and the label was hardcoded to "Policy v2" regardless of what actually existed in policy history (a fresh clone with no retrain has no v2). Fixed: it now approves the real latest version in the version-history timeline through the same server-verified token as that section's own approval flow, and displays whichever version and approver that call actually returns.
10. **The approval gate was enforced only in the React UI, not the API** — found in a self-audit. `POST /api/policy/approve` accepted any client-supplied `approved_by` string with zero server-side check; a direct API call (`curl`) could approve any policy version as anyone, contradicting the project's own "real Supabase sign-in + face match required" claim. Fixed in `backend/auth.py`: the endpoint now requires a short-lived signed token that the backend only mints after (a) independently verifying the Supabase session against Supabase's own `/auth/v1/user` endpoint and (b) re-fetching the enrolled face descriptor and re-computing the match **in the backend process itself**, not trusting the browser's "it matched" claim. `POST /api/policy/approve` reads the approver's identity from the token's verified claims, never from client input. Seven regression tests in `TestApprovalAuth` (`tests/test_pipeline.py`) cover the forged-token, tampered-signature, expired-token, and old-spoofable-payload-shape cases end-to-end.
11. **CORS was wide open** (`allow_methods=["*"], allow_headers=["*"]`) — flagged in the same audit as low-severity-but-worth-fixing. Tightened to the actual method/header set the frontend uses (`GET`/`POST`/`DELETE`, `Content-Type` only). Noted explicitly in the code that CORS restricts which browser origins may *read* a response, and is not itself an authentication mechanism — the real security boundary for approvals is the signed token in `auth.py`, unaffected by this change.
12. **Blast-radius internal review notes showed `$` instead of `₹`** — found doing a real click-through of the deployed dashboard (a good demonstration of why automated tests alone don't catch everything). `annotate_blast_radius`'s prompt never told the model which currency the numbers were in, unlike `generate_customer_letter`, added earlier, which already had this instruction. Fixed by adding it here too; regression-tested by capturing the actual prompt sent and asserting the currency instruction is present.
13. **`POST /api/policy/retrain` had no rate limit** — anyone could spam decision-tree retrains for free compute; combined with #10 (before it was fixed), an unauthenticated caller could create *and approve* policy versions end-to-end. No auth is required to retrain (that was never the claim — only *approving* needs a verified identity), but unlimited calls still needed a bound. Fixed with a simple in-memory rate limit (20/minute).
14. **`openai/gpt-oss-120b` (a reasoning model) silently returning empty answers** — under a multi-constraint prompt (jargon-avoidance + tone + grounding rules at once), the model sometimes spent its entire token budget on internal deliberation and returned `finish_reason: "length"` with an **empty** `content` field — not an error, just nothing. Found while building the customer-facing letter feature. Fixed with `reasoning_effort="low"` plus more token headroom; the function now raises a clear error instead of ever returning an empty string, regression-tested.
15. **Confirmed, exploitable path traversal in the multi-tenant workspace endpoints** — found in a security audit and verified with a live request, not just inferred: `GET /api/tenants/{tenant_id}` and the delete endpoint built a filesystem path directly from the client-supplied `tenant_id` with no validation. FastAPI's `{tenant_id}` path converter blocks a literal `/`, but not `\` — and on Windows (this project's dev platform) a backslash *is* a path separator, so `GET /api/tenants/..%5Cpolicy_history` successfully returned the full contents of `data/policy_history.json` through the tenant-lookup endpoint. Fixed in `backend/dataset.py`: `tenant_id` is always a `save_tenant()`-generated `uuid4().hex[:12]`, so any value not matching that exact 12-character-hex shape is now rejected outright before it ever reaches a filesystem path. Two regression tests cover this — one exercising `get_tenant`/`delete_tenant` directly with four different traversal payloads (backslash, forward-slash, URL-encoded, and a `....//` double-encoding bypass attempt), one hitting the real FastAPI endpoint end-to-end and asserting the leaked file's real field names never appear in the response.
16. **The readiness gate only floored recall, not precision** — found while testing the Autonomous Risk Policy Engineer's first live runs: a 54.5%-precision candidate (40 false positives) was marked `APPROVAL_ELIGIBLE` because the only hard threshold was `recall >= 95%`. Fixed by adding a precision floor matching this project's own v1 baseline (85%) as an equally-weighted gate.
17. **A statistically naive fairness-severity threshold** — the autonomous engineer's fairness gate flagged a candidate as "severely" unfair from a segment false-positive ratio of 57×. The absolute rate behind that ratio was one false positive in a 52-person segment; with a near-zero population-wide baseline (0.03%), any single misclassification produces a huge *ratio* that looks catastrophic but isn't a pattern. Fixed by requiring both a large ratio (>5×) **and** a real absolute rate (>2%) before calling something severe — the same statistical caution `src/portfolio_conflict_check.py`'s own "small sample, reported not hidden" framing already argues for.
18. **The economic intervention optimizer's 5-action ladder silently collapsed to 2 actions** — first version used the fully adversarially-hardened `discovered_policy_final.joblib`'s own `predict_proba` as the risk score. That tree's leaves are near-pure (0 or ~1) post-hardening — checked directly: 934 of 935 held-out customers landed outside the 0.1–0.9 band — so every intermediate action (`STEP_UP`/`DELAY`/`MANUAL_REVIEW`) was mathematically never optimal; the "graded ladder" was a binary rule with unused extra steps. Not a coding bug, a real property of this near-perfectly-separable synthetic dataset (device/address sharing is close to a perfect signal by construction). Fixed by separately fitting a `RandomForestClassifier` purely for a continuous risk score (never registered/approved as a competing policy — the governed decision tree still makes the actual ALLOW/FLAG call), and by adding a synthetic decision-boundary sweep (same diagnostic-sweep technique as `attack_coverage.py`) to prove the ladder mechanism itself grades correctly even though the real observed data doesn't exercise every rung. The honest finding is disclosed in the tool's own output (`separability_note`), not hidden to make the feature look more impressive.
19. **The first version of the difficulty-tiers evaluation measured the wrong thing entirely** — it retrained a fresh `DecisionTreeClassifier` on each of the "easy"/"ambiguous"/"adversarial" tiers' own data. Every tier scored ~100% precision/recall, with "adversarial" scoring *higher* net value than "easy" - a strong signal the experiment was broken, not evidence the policy is robust. Root cause: a freshly-retrained tree just re-learns whatever separates that tier's own synthetic labels, which measures "can a decision tree fit this data" (almost always yes), not "does an already-deployed policy generalize to harder data it's never seen." Fixed by scoring the already-frozen, never-retrained `discovered_policy_final.joblib` against fresh out-of-sample populations (seed 777, distinct from the training seed) instead - this produced the real, meaningfully degraded numbers (precision dropping to 74.7%/80.8% on the harder tiers) that are actually informative.

## Security audit — what was tested, what was found

A focused pass, not a paid third-party audit — but real testing against a running instance, not just code review:

- **Prompt injection / tool abuse**: the LLM is never given a tool-calling interface it could misuse — every LLM call in this project (`backend/llm.py`, `backend/agent.py`) returns structured JSON that is validated against a fixed whitelist (real feature names, real customer IDs) before use; nothing an LLM outputs is ever executed, evaluated, or used to construct a filesystem/database query. The one place adversarial input reaches an LLM at all is CSV column-mapping inference (`infer_column_mapping`) — a malicious column name can at worst cause a bad mapping, which `apply_mapping`'s required-column check rejects with a clear error, not a bypass.
- **Policy injection**: confirmed by code inspection and the architecture itself (see the Autonomous Risk Policy Engineer section of the README) that the LLM can only propose *feature names from a whitelist* — never a numeric threshold, never an executable rule. Every threshold in every policy this project has ever produced (v1 through the autonomous engineer's candidates) was fit by `scikit-learn` from real training data.
- **Approval bypass**: addressed at length above (#10) — a signed, server-verified, short-lived token is required, independent of client claims.
- **Tenant isolation / path traversal**: a real, exploitable vulnerability was found and fixed (#15 above).
- **Data poisoning via malformed CSV upload**: `apply_mapping` coerces `amount`/`day` to numeric with `errors="coerce"` and drops unparseable rows rather than crashing or silently treating garbage as zero; missing required columns raise a clear `ValueError` before any analysis runs. No `eval`, `exec`, `pickle.loads`, or shell invocation exists anywhere in `backend/` or `src/` (verified by direct search) — a malicious CSV's cell contents are never interpreted as code in any code path.
- **LLM hallucination entering a policy decision**: structurally prevented, not just discouraged — see "policy injection" above. The one place an ungrounded LLM claim could reach a user is the AI Autopsy Agent's free-text `root_cause`/`missed_signals` fields, which are advisory narrative only and never gate an approval decision; the gates that do decide `APPROVAL_ELIGIBLE`/`BLOCKED` are computed entirely from `scikit-learn`/`pandas` output.

## Technical deep-dives kept out of the main pitch

These are real, load-bearing parts of the system — kept here rather than the README because they're implementation detail a judge doesn't need to read to understand the product, not because they're less important.

### Doubly-robust off-policy evaluation — full method

Held-out precision/recall is only valid because this synthetic dataset has full ground truth for every customer. A real deployment doesn't get that: you only have logged outcomes from whatever policy was actually running, and the customers that policy acted on aren't a random sample. Naively replaying logged outcomes to score a new policy is biased.

The baseline policy is a hard deterministic threshold (`amount > ₹25,000`), for which off-policy evaluation is mathematically undefined (propensity is exactly 0 or 1 — zero overlap). The project models the logging policy as a smoothed, stochastic version of the same threshold (realistic — human review of a threshold is never perfectly consistent), which makes valid off-policy evaluation possible, and implements a real **doubly-robust (DR) estimator** (Dudík, Langford & Li). Because this is synthetic data, the true value of the target policy is directly computable, so the DR estimator's recovery of it using only logged (partial) data can be verified — something a real deployment never gets to check.

Result: DR estimate off from oracle truth by only 2.2%, vs. 6.9% for the Direct Method alone and 18.5% for IPS alone — demonstrating why doubly-robust estimation is preferred. Run it: `python src/off_policy_eval.py`.

### Portfolio conflict check — what it found

A policy with great aggregate precision/recall can still be a bad policy to ship if it silently punishes one customer segment far more than others. `src/portfolio_conflict_check.py` breaks the false-positive rate down by account-age and purchase-amount bands and flags outliers. It found one: the ₹5-15k purchase band has an 8.2x higher false-positive rate than the population average under the new policy — small sample (2/52), but reported, not hidden.

### Policy version history — why the comparison is fair

`backend/policy_history.py` lets a reviewer retrain a genuinely different decision tree (different `max_depth`/`min_samples_leaf`) and get its real precision/recall/FP on the exact same held-out split as the original v1 (same random seed, same ring-grouping — verified by a regression test that v1's retrained metrics reproduce the original pipeline's numbers exactly).

### Compliance dossier

`backend/dossier.py` (`GET /api/dossier`) assembles every stage's real computed output — held-out metrics, adversarial log, co-evolution result, off-policy evaluation, portfolio conflict, blast radius — into one PDF via ReportLab, with an approval record at the end if the policy's been signed off.
